Problem — no page fetches data through an SSR-aware interface, so ssr:true routes server-render empty shells, the blanket no-cache header stops those shells being cached, and the client-only auth guard leaves SSR routes unguarded on the server — the migration's SEO goal is structurally unreachable.

Solution — public pages fetch through useAsyncData backed by the Record repository so data crosses the seam during server render; replace the blanket no-cache with per-route cache rules; make the route guard universal.

  • Delivers the SSR migration's actual goal: crawlable content
  • Server half of candidate 3; consumes candidates 1 and 9
  • One data path, two adapters: server render, client navigation
  • Hydration mismatches become detectable, not endemic

Top recommendation

One Record store, entered via the query builder

Start with candidate 2 — the pure record-query builder is small, gives the codebase its first testable interface, and is the natural first brick of candidate 1. Then deepen the Record repository: it passes the deletion test hardest (20+ call sites re-absorb draft-or-published logic if it goes), and it's the module the SSR migration keeps tripping over. Candidate 6's sweep can happen alongside as a mechanical warm-up, and candidate 7's $fetch rebuild is the caller-side half of the same effort. Candidate 8 (the NR7 section module) is the highest-value follow-on once the Record repository exists — it sits directly on top of it, and candidate 9 dissolves the cache-shaped stores those editors currently lean on. Candidate 10 is the payoff: once the repository and useAsyncData keys exist, public pages fetch server-side and the SSR migration actually delivers crawlable content. Independent of all of it: work the fix-now list first.
